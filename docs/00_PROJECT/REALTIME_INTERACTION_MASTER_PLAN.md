# 丑橘学习助手｜实时互动系统主线与最终架构基线

> 文档状态：候选冻结基线，位于审查分支；合并到 main 并经用户确认后，作为后续施工的项目级依据。  
> 编写依据：此前《实时互动系统架构审查报告》及后续统一施工讨论；当前源码基线 commit `f3a79b7a3995ad0fa8f18d86c8ed270715f0118e)。  
> 本文冻结目标和架构原则，不宣称所有能力已实现或验收通过。

## 1. 为什么需要这份文件

本项目此前已经反复分析过实时观察、跨屏累计、题目隔离、多模态请求、悬浮层遮挡和测试中心等问题。后续单点故障不能覆盖或重写这些决定。

任何一次新反馈都应被登记为有边界的子任务，先关联现有需求、架构决策和验收条目，再分析根因与最小修复。除非有源码证据表明冻结架构本身无法满足需求，且用户明确批准变更，否则不得因局部问题另建一套平行链路。

## 2. 产品主线目标（冻结）

构建一个面向手机刷题场景的实时互动学习助手：

1. 用户在第三方刷题 App 中阅读材料、题干和选项时，Hanako 能够持续获取当前可观察的屏幕信息；用户滚动后，能够把有证据关联的同题内容进行累计。
2. 用户能够通过悬浮球唤起迷你对话窗口，针对当前题目提问；打开迷你窗口本身不应触发无意义的重复扫描，发送问题时优先使用可证明新鲜、对应当前题目的上下文快照。
3. 系统能够联合使用无障碍文本、本地 OCR 与真实图像证据。图表、几何图形、公式等不能仅因为 OCR 无法表达就被默默丢弃。
4. 系统只把有证据支持的内容作为确认信息；未确认内容需显式标记，缺失关键数据时向用户说明，不能猜答案。
5. 用户和开发者能从实时互动测试中心追踪一次问题对应的采集、过滤、上下文、图像发送和模型响应，并可导出、复制这些真实数据。
6. 用户不必为了诊断问题反复截图或手动拼接大量日志；局部错误可由 traceId 和证据 ID 定位。
7. 系统应保留必要历史证据以便复核，同时在不影响活动题的前提下执行明确的容量和隐私策略。具体保留配额仍需产品决策，不能擅自当作已冻结数值。

## 3. 唯一推荐架构（冻结）

统一的数据流：

屏幕/无障碍观察
→ 单一观察与采集协调入口
→ 原始证据追加写入 EvidenceStore
→ 可重算的 EvidenceFilter
→ QuestionContextAssembler 产出唯一题目上下文快照
→ 迷你聊天读取快照
→ 统一请求构造逻辑根据实际端点能力生成文本与图像载荷
→ 模型适配器发送
→ RequestTrace 记录实际上下文、证据引用、图像数量、能力判定与结果
→ 实时互动测试中心只读同一链路的数据。

### 3.1 证据层是唯一事实来源

- 原始证据必须保留稳定 evidenceId、采集时间、来源应用/窗口、来源类型、原始文本或节点、OCR 原文及行信息、图片引用/哈希、可用性与错误原因（适用字段以实际模型为准）。
- 原始记录原则上只追加。过滤、排序、合并和上下文整理不能静默覆盖原文。
- 派生结果必须能够追溯到原始 evidenceId，并记录过滤规则版本与理由。
- 图片元数据与图像文件应具有可核查的关联；文件丢失或持久化失败必须显式报告。
- 当前实现采用原生 SQLiteOpenHelper 保存元数据、私有目录保存图像资产。架构基线不强制迁移至 Room；不得仅为了采用某项技术而改变依赖或重写存储层。

### 3.2 单一观察链路，不保留互相矛盾的上下文真相

- 复用并整合现有无障碍服务、采集器、屏幕变化判定、OCR 组织、跨视口合并和证据记录能力。
- 不新建第二套 OCR 管线、文本池或题目上下文来源来绕过现有问题。
- ScreenContextManager、旧文本池或片段对象若仍存在，只能作为兼容层、采集中间产物或诊断状态；不得与 AssembledQuestionContext 竞争成为第二个权威上下文。
- 每个请求必须能说明它使用了哪个 questionId/context version/evidenceIds，以及这些内容为何被判断属于当前题目。
- 同题关联证据不足时必须保持分段或标为待确认；不得凭相似文本把不同题目拼接为同一题。

### 3.3 上下文完整性与新鲜度

统一上下文至少应能表达：
- 当前题目标识和版本；
- 题干、材料、选项及图像/图表/公式证据的有序引用；
- 已确认、已排除、待确认内容及各自理由；
- 新鲜度与完整性状态；
- 缺失项、不可用图像和过滤失败；
- 来源证据 ID 及更新时间。

状态不能只由选项数量或字符数决定。材料可能在其他视口，选项齐全也不代表材料完整。上下文无法证明对应当前屏幕时，不得把旧缓存伪装成最新结果。

### 3.4 多模态请求必须验证真实载荷

- 视觉能力判定必须与实际端点/协议配置一致；不能仅凭模型显示名称推断中转站必然支持图片。
- 只有实际存在、可读取且被构造进请求体的图片，才计入“已发送图像数”。
- 请求追踪必须区分：有图像证据、图像文件可用、端点声明支持、请求载荷含图、请求成功、模型实际返回。这些不是同一状态。
- 不支持视觉的端点需要明确提示图片没有发送，并说明文本上下文的限制；不可假装已完成视觉理解。
- 图片数量、尺寸、区域裁剪和上下文长度要有明确预算，并在截断时显式记录可能丢失的信息。自动区域裁剪是否完成必须以源码和测试为准，不能由枚举值存在来推断。

### 3.5 悬浮层、输入法与截图事务

- 当请求路径或测试操作确实需要重新截图时，应先隐藏可能遮挡目标屏幕的 Hanako 浮层，并根据采集实现需要处理输入法；只把覆盖区域涂黑不能恢复其背后的刷题页面。
- 只有在隐藏/收起完成后产生的新帧，才可以被认定为本次无遮挡采集结果；旧缓存帧不得冒充。
- 必须覆盖成功、失败、超时和异常路径，保证悬浮层与输入法在 finally 等价的收尾路径中按原状态恢复。
- 采集失败不能导致悬浮球永久消失、重复添加窗口、重复发送请求或清除本轮已保存证据。
- 后台观察和请求时补救采集必须清晰区分，避免两个并发链路重复识别、相互覆盖或产生竞态。

### 3.6 实时互动测试中心必须与主链路同源

测试中心是只读诊断与受控重放界面，不是第二套观察器或证据池。它应展示真实的运行状态、原始采集记录、过滤结果、上下文、图像资产、请求载荷状态和响应追踪。

必须区分“未运行、成功、失败、待真机验证”。重放已保存证据应当重跑过滤/组装，而不是在没有提示的情况下重新截图或触发模型请求。

导出和分享应默认脱敏 API Key、令牌、密码；是否允许导出完整题目正文、图片以及脱敏 prompt 预览，需要在明确的隐私边界内处理。测试中心长按选择文本、模块级复制和 TXT 导出属于用户明确提出的功能需求。

## 4. 必须保留的既有能力

在没有证明其有缺陷前，优先复用下列已有算法与组件，而不是从零替换：

- ScreenChangeDetector：屏幕变化分类与阈值；
- ViewportMerger：跨视口去重与有序合并；
- PoolInjection：既有注入判定算法，后续逐步改为消费统一上下文；
- ScreenContentQuality：屏幕内容质量门控；
- OcrTextOrganization：结合坐标恢复阅读顺序；
- 无障碍服务与本地 OCR 采集；
- 现有模型 provider 适配器和协议实现；
- ChatSessionHolder 中已有的切题/历史隔离逻辑。

保留不等于禁止修复：任何更改都必须有明确根因、针对性测试和回归测试。

## 5. 禁止偏离的规则

1. 不因单点故障就新建第二套文本池、截图管线、上下文 assembler 或测试数据源。
2. 不把“编译通过”“纯函数单元测试通过”描述成“实时互动已完成”。
3. 不以 OCR 字符数、选项齐全或配置中的视觉开关证明材料完整、图像实际发送或模型成功理解。
4. 不用猜测、硬编码答案或静态示例掩盖证据缺失。
5. 不静默清除、改写或因关闭实时模式而删除原始证据。
6. 不引入与当前任务无关的架构迁移、外部运行时、重型依赖或新的业务功能。
7. 不未经用户确认调整最终目标、数据生命周期、隐私导出边界或核心数据流。
8. 不将任何局部修复自动升级为主线架构变更。需要变更时，先提出决策记录、影响面和替代方案。

## 6. 阶段路线与通过条件

阶段 0：主线和项目状态治理
- 产物：本文件、PROJECT_STATE、ARCHITECTURE_DECISIONS。
- 通过：主线文档进入项目默认分支并被后续施工提示词引用。

阶段 1：原始证据和测试中心基础
- 通过：能持久化真实 evidenceId、来源应用、时间、原文/图像引用和失败状态；重启后可检查历史证据；测试中心读取同一数据源。
- 注意：源码存在相关类不等于该阶段已验收。

阶段 2：单一观察链路
- 通过：观察事件只经权威采集入口写证据；发送消息不再意外触发重复的同步 OCR；读取上下文足够快；实时关闭不销毁历史证据。

阶段 3：过滤、题目关联与跨屏累计
- 通过：跨视口顺序正确、不重复、不虚构连续性；切题后旧题不会混入；关键材料不会因排序/截断静默丢失；UNCERTAIN 有理由且可回溯。

阶段 4：真正的图文请求
- 通过：请求 trace 能证明当前 context/evidence/image IDs 与实际载荷对应；视觉能力不支持或图片不可用时明确降级；图表/公式样本经过真实端点验证。

阶段 5：迷你聊天接入
- 通过：打开迷你窗不触发意外扫描；提问使用最新可证明的上下文快照；请求与证据 trace 一一关联。

阶段 6：端到端回归与真机验收
- 通过：编译、定向测试、完整测试和真机结果分开报告；窗口隐藏/恢复、输入法、第三方应用、跨屏材料、图像发送、导出/复制均有明确结果。

阶段可并行开发，但不能越过依赖条件宣称验收完成。当前状态见 PROJECT_STATE.md。

## 7. 当前优先处理的子任务

这是基于用户最近一次真机反馈登记的当前问题，不改变最终架构：

- RTI-001：截图/实时采集结果中，Hanako 悬浮球和迷你对话窗口遮挡刷题页面。调查实际采集时序、隐藏策略、旧帧判定及输入法状态，修复后确保异常路径恢复。
- RTI-002：模型识别到题干和选项，却没有获得计算所需的材料数据。必须通过 trace 追踪“实际采集 → 原始证据 → 过滤 → 上下文 → 最终请求文本/图片载荷”，精确判定缺失环节。
- RTI-003：实时互动测试中心顶栏缺少完整 TXT 导出/分享入口，模块缺少复制全部内容，长文本缺少像聊天页面一样的长按选择复制交互。必须复用既有 UI 机制并保持滚动、按钮可用。

这三个任务属于当前阶段的实现和诊断工作，不代表它们已经修复。先查源码与请求 trace，再实施最小修复；不得拿增加一个 UI 按钮代替证据链验收。

## 8. 每轮施工流程

每个新问题按以下格式登记：
- 问题 ID、用户可见症状、复现步骤；
- 关联的主线章节与架构决策 ID；
- 当前代码 commit、测试 APK 版本/commit（可获得时）、设备/目标应用；
- 证据等级：源码已证实 / 自动化测试已证实 / 旧日志支持 / 合理推断 / 待真机验证；
- 根因与证据；
- 最小修复边界和明确禁止范围；
- 定向测试、回归测试、完整测试、真机验收结果；
- 对主线/架构是否有影响；
- 剩余风险和下一步。

每次给 TRAE 的施工提示词都必须写明：阅读本文件、PROJECT_STATE 和相关决策；只执行指定子任务；不得自动扩展范围；结束后提供真实输出、代码差异、测试结果、APK 标识和更新状态文档的建议。

## 9. 证据与来源等级

- 源码已证实：只说明代码路径现状，不证明运行时有效。
- 自动化测试已证实：只说明测试覆盖的行为成立，不代替真机。
- 日志支持：必须能用 traceId/时间/证据 ID 对应到实际请求。
- 合理推断：显式标记并列出验证方法。
- 待真机验证：不得使用“已完成”“已修复”等结论。

## 10. 仍需用户决策的事项

以下不能由架构文档擅自替用户决定：
- 历史证据、图片和题目元数据的容量/保留期限具体数值；
- 测试中心是否展示完整题目正文、图片及脱敏 prompt，默认可见范围和二次确认方式；
- 自动清理和用户手动清理的产品交互；
- 任何会影响隐私、存储规模、费用或权限的架构变更。

这些事项在明确决策前采用保守实现并记录限制，不把过去报告中的建议数值视为已批准的产品决定。
